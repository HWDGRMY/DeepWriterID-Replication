# DeepWriterID Replication on CASIA-OLHWDB

## 项目简介

本项目是对论文《DeepWriterID: An End-to-end Online Text-independent Writer Identification System》的完整复刻，基于 **CASIA-OLHWDB 2.0-2.2 在线手写文本数据集（1019 位书写者）** 进行验证。

原论文使用 NLPR 数据库（187 位书写者），笔者未能找到该数据集的公开下载渠道，因此采用同源的 CASIA-OLHWDB 进行复刻。

## ⚠️ 重要更新：数据流修复

**本项目早期版本存在一个严重缺陷**：拐点检测阈值与坐标量级不匹配，导致 DropSegment 从未真正生效，伪字符退化为“扁行”而非“方形”。

该缺陷已修复。修复后：

- 拐点检测恢复正常，伪字符切分为方形
- DropSegment 真正随机删除笔画片段
- 20-test 评估每轮结果不再相同，具备统计意义

修复详情见「踩坑记录」章节。

> **📌 更新**：本项目还有一个性能更好的 **v2 版本**，采用 ConvNeXt V2 骨干网络替代原始 DCNN，在相同的 1019 类闭集识别任务上达到了 **98.04%** 的页面级准确率（20-test 协议）。详情请见：[DeepWriterID-v2](https://github.com/HWDGRMY/DeepWriterID-v2)。

## 核心成绩

本项目报告两组结果，分别对应两种不同的数据流状态：

| 模型 | 数据流状态 | 协议 | 页面级准确率 |
| :--- | :--- | :--- | :--- |
| DCNN（原始） | 缺陷数据流（扁行，DropSegment 失效） | 1-test | **95.09%** (969/1019) |
| DCNN（微调） | 修复数据流（方形，DropSegment 生效） | 1-test | **90.19%** (919/1019) |
| DCNN（微调） | 修复数据流（方形，DropSegment 生效） | 20-test | **92.74%** (945/1019) |

**对比参考**：

| 项目 | 协议 | 类别数 | 页面准确率 |
| :--- | :--- | :--- | :--- |
| 原论文（NLPR） | 20-test | 187 | 95.72% |
| 本项目（缺陷数据流） | 1-test | 1019 | 95.09% |
| 本项目（修复数据流） | 20-test | 1019 | 92.74% |

> **注**：需要说明的是，虽然本项目类别数约为原论文的 5.4 倍，但训练集样本量也相应增加，约为原论文的 2 倍，因此任务难度的提升并非完全与类别数成等比例关系。此外，原论文在测试时对每个伪字符生成 20 个 DropSegment 变体并进行概率平均，且测试页为固定内容；本项目测试页文本内容随机，未划分独立验证集。因此，上述数字的直接对比存在方法学差异，仅供参考。

## 💻 硬件约束：预处理流水线对系统的真实需求

本项目的计算瓶颈不在于神经网络的前向/反向传播，而在于 **CPU 密集型的数据预处理流水线**。

### 1. 内存带宽与并发瓶颈

- `DataLoader` 配置为 16 个并行 Worker（`num_workers=16`）。
- 系统物理内存达到 **60GB** 时，可稳定运行，单轮耗时约 **15 分钟**。
- 内存低于 60GB 时，高并发多进程内存争用将触发 `Bus error` 或 OOM Killer。**即使 CPU 核心数提升至 96 核，如果内存仅 32GB，内存依然是无法逾越的瓶颈。**

### 2. 单核性能对预处理时间的决定性作用

- 每轮训练处理约 **85 万个动态增强的伪字符**，每次迭代包含：拐点检测、OpenCV 图像渲染、直方图均衡化及路径签名计算。
- 上述操作难以高度并行化，**单核主频与 CPU 架构** 对完成效率起决定性作用。
- 本项目能维持 15 分钟一轮的吞吐量，得益于 **AMD EPYC 9754 的高单核主频与浮点计算能力**。若使用低主频老旧架构，即便 vCPU 数量充足，单轮耗时也可能延长至 30 分钟以上。

### 3. 显卡利用率的真实情况

- `batch_size=256` 下，RTX 4090D 显存占用稳定在 **9.5GB 左右**，GPU 核心利用率长期低于 **40%**。
- GPU 算力大幅冗余，计算瓶颈完全位于前端 CPU 数据流水线上。

## 🧠 Dropout 正则化策略

由于本项目面对 **1019 个类别** 的超大分类任务，直接套用原论文的 Dropout 配置（0.3, 0.4, 0.5, 0.5）会导致严重欠拟合。

本项目在 `src/models/dcnn.py` 中的调整：

- 全连接层 `fc1` 和 `fc2`：**0.2** Dropout
- 输出层 `output`：**0.2** Dropout

该配置既能防止过拟合，又能保证训练初期梯度正常传递。

## 🎲 随机种子与数据划分说明

### 1. 随机种子状态（默认）

当前 `preprocess.py` **未设置固定的随机种子**，每次运行都会产生全新的随机划分，最终测试准确率可能在 **94.5%~95.5%** 之间轻微浮动。

### 2. 固定划分的方法

若希望每次划分结果一致，可在 `preprocess.py` 的 `main()` 开头添加：

```python
random.seed(42)
```

由于不同操作系统（Linux vs Windows）下文件遍历顺序不同，该操作也无法保证 100% 完全一致。

### 3. 严格复现 95.09% 成绩的方法

本项目宣传的 **95.09%** 基于 **特定的 `metadata.csv` 划分文件** 与 **已训练好的 `dcnn_best.pth` 模型权重**。

复现步骤：

1. 使用项目提供的 `metadata.csv`
2. 根据本地路径修改文件中的路径
3. 配合笔者训练的 `dcnn_best.pth`
4. 运行 `python scripts/evaluate.py`

> 自行训练时，由于硬件和随机性差异，准确率会有一定波动。

## 📂 数据集划分说明

### 1. 数据集概况

CASIA-OLHWDB 2.0-2.2 共 **1019 位书写者**，每位 **5 页**。全部数据按作者合并后重新划分，确保训练集与测试集作者完全重叠（闭集识别）。

### 2. 划分策略

采用 **4:1 划分**：每位作者随机 1 页测试，其余 4 页训练。

| 数据集 | 每位作者页数 | 作者数 | 总页数 |
| :--- | :--- | :--- | :--- |
| 训练集 | 4 页 | 1019 | 4076 页 |
| 测试集 | 1 页 | 1019 | 1019 页 |

### 3. 为什么没有划分验证集？

**原论文做法**：仅划分训练集（2 页/作者）和测试集（1 页/作者），未设置独立验证集。

本项目沿用原论文做法，原因是数据量约束：每位作者仅 5 页，若划分验证集只能采用 3/1/1 方式，训练数据减少 25%，可能导致泛化性能下降。此外，验证集规模较小（约 1019 页），反复用于模型选择也容易过拟合验证集。

### 4. 未划分验证集的方法学局限

由于训练时未划分独立验证集，本项目采用了 **每轮在测试集上评估并保存最佳模型** 的机制。这导致测试集被同时用于：

1. 每轮性能评估
2. 最佳模型选择（保存最佳 epoch 对应权重）

因此，**报告的准确率是测试集上的最优选择结果，存在乐观偏差，并非严格无偏泛化估计**。

### 5. 展望

- 扩充数据规模，支持训练集/验证集/测试集严格划分
- 引入独立验证集用于模型选择，测试集仅最后评估一次

## 🕳️ 踩坑记录

### 坑点 1：拐点检测阈值与坐标量级不匹配（最严重）

- **现象**：DropSegment 从未真正生效；20-test 评估每轮结果完全一致；伪字符切分退化为“整行作为一个伪字符”。
- **根因**：数据加载器 `load_wptt_page` 把坐标除以了 10，坐标量级变为 0~720。但拐点检测的 `threshold` 沿用未除以 10 时设计的 **180**。缩放后弯曲值也随之缩小 10 倍，最大值只有约 150，**180 阈值在两层都检测不到任何拐点**。
- **修复**：将 `detect_corners` 的 `threshold` 从 **180** 改为 **3**，与缩放后坐标匹配。
- **影响**：修复后 DropSegment 真正开始随机删片段，伪字符切分为方形，20-test 评估每轮结果不再相同。

### 坑点 2：多笔画位图被虚假直线连接

- **现象**：某些字符的渲染图中，两个独立的笔画之间出现不存在的直线。
- **根因**：`render_trajectory_to_bitmap` 用 `cv2.polylines` 一次性画完所有点，抬笔点 (-1, 0) 被当作画线路径的一部分。
- **修复**：按 `-1` 分段绘制。遍历所有点，遇到 -1 就结束当前笔画并开始新笔画。

### 坑点 3：签名计算被抬笔点污染

- **现象**：路径签名数值异常，模型难以收敛。
- **根因**：`signatory.signature` 把 (-1, 0) 当成真实的坐标跳变点，导致积分路径出现巨大跳变。
- **修复**：在调用 `signatory.signature` 之前，先 `points = points[points[:, 0] != -1]` 过滤掉所有抬笔点。

### 坑点 4：多进程下 CUDA 初始化失败

- **现象**：`RuntimeError: Cannot re-initialize CUDA in forked subprocess`。
- **根因**：`DataLoader` 使用 fork 多进程时，子进程会继承父进程的 CUDA 上下文，导致冲突。
- **修复**：把所有 CUDA 相关操作放在 CPU 上进行；确保 `signatory.signature` 的输入张量在 CPU 上。

### 坑点 5：多进程共享内存溢出

- **现象**：`Bus error` 或 `Killed`，进程被系统强制中断。
- **根因**：`num_workers=18` 时，多进程内存争用超过 60GB 上限。即使总内存 60GB，高并发下的瞬时峰值依然会触发 OOM Killer。
- **修复**：把 `num_workers` 降到 16，并把 `DataLoader` 的 `pin_memory` 设为 `False`，`prefetch_factor` 设为 `2`。

## 🔁 微调模式：从 95.09% 模型继续训练

### 背景

修复拐点检测阈值缺陷后，数据流发生根本变化：

- 伪字符从“扁行”恢复为“方形”
- DropSegment 从“从未生效”变为“真正随机删片段”

原 95.09% 模型是在缺陷数据流上训练的，其卷积特征可能不再完全适配新数据流。因此采用 **微调策略**：以 95.09% 模型为预训练基础，继续训练 50 轮。

### 微调配置

```yaml
pretrained_path: outputs/checkpoints/dcnn_best.pth
batch_size: 192
epochs: 50
initial_lr: 0.0005
num_workers: 16
multiprocessing_context: fork
```

**关键设计**：

1. **只加载模型权重**：不恢复 optimizer/scheduler 状态，避免旧动量历史干扰
2. **学习率与从零训练一致（0.0005）**：保证模型有足够更新幅度适应新数据流
3. **保存为独立文件**：`dcnn_finetune_best.pth` / `dcnn_finetune_latest.pth`
4. **独立日志**：`training_log_finetune.csv`
5. **每轮评估**：沿用 8/8/8 的 worker 数

### 运行方式

```bash
python scripts/train.py
```

### 结果解读

**为什么微调结果（90.19% / 92.74%）低于原 95.09%？**

两者基于**完全不同的数据流**：

| 对比项 | 原 95.09% | 本次微调 |
| :--- | :--- | :--- |
| 拐点检测阈值 | 180（失效） | 3（有效） |
| 伪字符形态 | 扁行 | 方形 |
| DropSegment | 从未生效 | 真正生效 |
| 训练字符级准确率 | 13.16% | 7.36% |
| 任务难度 | 较低 | 较高 |

原 95.09% 是在 DropSegment 失效、伪字符退化为扁行的条件下取得的，本质上是**任务难度被弱化后的结果**。本次微调在修复后的数据流上训练，任务难度恢复正常，字符级准确率从 13.16% 降至 7.36%，说明模型在更严格的正则化条件下学习。

**为什么从零训练可能更适合？**

原 95.09% 模型的卷积核是在“扁行伪字符”上训练的，其特征响应针对宽窄条带的空间分布。修复后伪字符变为方形，特征图的空间布局完全改变。微调相当于“带包袱搬家”，前半程在挣脱旧特征束缚。如果从零训练，模型会直接在修复后的数据流上寻找最优解。
